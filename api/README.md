# STEP lab platform — API

Express + PostgreSQL backend for the STEP Laboratory's internal platform. Serves the React frontend in [`../app`](../app).

## Stack

Express 4 · PostgreSQL via `pg` · JWT auth (`jsonwebtoken`, `bcryptjs`) · `helmet` and `cors` · `multer` for uploads · `exceljs` for spreadsheet import and export · Jest and Supertest for tests.

## Running locally

Requires Node 20 and a PostgreSQL database.

```bash
cd api
cp .env.example .env      # then edit it
npm install
npm run migrate           # apply schema
npm run seed              # create the admin user and reference data
npm run dev               # nodemon on http://localhost:3001
```

| Script | Does |
|---|---|
| `npm run dev` | nodemon, reloads on change |
| `npm start` | plain node, used in production |
| `npm run migrate` | applies pending migrations |
| `npm run seed` | inserts admin user, inventory zones and templates |
| `npm test` | Jest suite, serially |

### Environment

| Variable | Example | Notes |
|---|---|---|
| `DATABASE_URL` | `postgresql://user:password@host:5432/step_db` | required |
| `JWT_SECRET` | a long random string | required; tokens are signed with it |
| `PORT` | `3001` | |
| `FRONTEND_URL` | `http://localhost:5173` | the CORS origin |

## Endpoints

Everything is mounted under `/api`, plus a `GET /health` returning `{ status: "ok" }`.

| Prefix | Handles |
|---|---|
| `/api/auth` | register, login, current user |
| `/api/admin` | user administration and role changes |
| `/api/experiments` | experiments and their steps |
| `/api/templates` | experiment templates |
| `/api/resources` | inventory — containers, locations, quantities, hazard codes |
| `/api/datasets` | measurement datasets attached to experiments |
| `/api/publications` | publication records and Web of Science import |

Route handlers are one file per prefix in `src/routes/`. `src/middleware/auth.js` verifies the JWT and enforces roles.

## Database

Migrations are numbered SQL files in `migrations/`, applied in filename order and recorded in a `_migrations` table, so `npm run migrate` is safe to run repeatedly and only applies what is pending. Each migration runs in its own transaction and rolls back on failure.

To change the schema, add the next numbered file — `013_your_change.sql` — rather than editing an existing migration. Migrations that have already run on the deployed database will not run again.

`npm run seed` is idempotent: it skips inventory zones and templates that already exist, and upserts the admin user.

> **Change the seeded admin password.** `src/seed.js` contains a default administrator with a placeholder password, and the production deploy runs the seed on every release. Log in once and change it, or override the seeded values before the first deploy.

## Tests

```bash
npm test
```

Tests need a **separate** database. Create `api/.env.test` with a `DATABASE_URL` pointing at it — for example a `step_test` database. `tests/globalSetup.js` applies all migrations to it once before the suite, and `tests/env.js` loads that file for every test so the pool never points at your development data.

Suites cover authentication, experiments and resources. They run with `--runInBand` because they share one database.

## Deployment

Render, configured in [`../render.yaml`](../render.yaml): a free-tier web service with `rootDir: api`, plus a managed `step-db` PostgreSQL instance. The start command runs `migrate`, then `seed`, then the server — both are idempotent, so every deploy converges the schema. `DATABASE_URL` comes from the managed database and `JWT_SECRET` is generated by Render.
